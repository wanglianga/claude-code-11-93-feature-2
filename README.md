# 环卫线路工作台（封路重排 + 转运站窗口预约演示）

浏览器端环卫线路工作台，包含两条随题固定的演示主线：

1. **封路重排**：调度员在地图与路线清单中查看道路限行、服务截止、每站估重、车辆载重与卸载点时段；司机按当前线路登记到站/扫码/称重/满溢/封路；客服按线路版本核查预约通知是否仍有效。
2. **转运站窗口预约（锁量 vs 到场排队）**：站长调整窗口（时段/容量）、临时停收、切换容量模式；调度员查看转运站队列与受影响站点并发出等待/改道安排；司机到场排队、过磅并确认调度安排。同一组数据下并列对比两种容量模式。

全部数据为随题固定的虚构数据，存于浏览器 IndexedDB，可一键重置重放；线路重排在 WebWorker 中计算。

## 技术栈

- React 18 + TypeScript + Vite
- IndexedDB（`idb`）：车辆、站点、路网、封闭、卸载点、通知、线路版本、回执、转运站窗口/预约/调度指令、事件日志全量落库
- WebWorker：重排方案（最小变更 / 全局重排）在后台线程计算
- 纯前端，无后端；nginx 托管静态资源（Docker）

## 随题固定的场景

### 主线一：封路重排

09:20，清运班组长收到通知：**清河桥（S1—S2）09:20–10:15 封闭**，T1 无法按原顺序进入 S2（S2 截止 10:00；绕行最短 42 分钟，10:02 才到，仍超截止）。

- T1：容量 5.0t、已载 3.0t，剩余 S1（估 0.7t）、S2（估 1.2t）
- T2：容量 4.0t、已载 0.8t，原路线 S3（0.8t）→ S4（0.7t），居民已获知预计到达
- S2 截止 10:00，S3 截止 10:30，S4 截止 11:00；卸载点 D1 开放 08:00–12:00
- 道路限制：市场高架（S2↔S4）限高 2.6m（T1 高 3.1m 不可通行）；车场↔S2 限宽 2.5m

点「生成方案」后页面**并列显示两个方案**（不只给一条最优线）：

- **方案 A · 最小变更**：S2 前置移交 T2，其余已通知顺序不变。T2 = S2→S3→S4，行驶 25 分钟（合计 31）；仅 S2 的 1 条通知需重发
- **方案 B · 全局重排**：T2 = S3→S2→S4，行驶 14 分钟（合计 20，省 11 分钟）；但 S2/S3/S4 共 3 条通知需重发（车辆变更、到达提前 10/7 分钟）

两案均通过吨位、限高限宽、截止时刻、卸载点时段核验；被排除候选（如「T1 承运 S2：绕行 10:02 到达，超过截止 10:00」）一并展示——不用“地图上可达”代替限制核验。

### 主线二：转运站窗口预约（本题数据）

**城西转运站只剩 10:00–10:30 一个窗口、可接收 4 吨**；调度 09:20 按随车清单为两车预约：**T1 估 2.5 吨、T2 估 2.0 吨**；T1 过磅后实际只有 **1.8 吨**。城北转运站（09:30–12:00，8 吨）为改道备选。

初始为**锁量模式**：T1 先锁 2.5 吨 → 剩余可锁 1.5 吨 < T2 估 2.0 吨 → **T2 暂时被挡**（等容量释放或改道）。两种容量模式的对比（页面内「锁量 vs 到场排队」面板按本题数据实时演算）：

| 对比维度 | 锁量（按预计吨位先锁窗） | 到场排队（过磅后才扣实际容量） |
| --- | --- | --- |
| 可接车辆 | 2 辆，但 T2 一度被挡，10:06 释放后才锁入（等不及就会改道，窗口余量空置） | 2 辆，按到场顺序全部接纳，估高不占坑 |
| 等待顺序 | 按预约锁定先后；被挡车辆等的是“容量释放” | 按到场先后 T1→T2；后车等的是“前车过磅完成” |
| 容量释放时刻 | **10:06**（T1 过磅，实 1.8 < 估 2.5，释放 0.7 吨） | 无锁量可释放：容量只在过磅时按实称扣减，剩余量随每次过磅才确定 |
| 司机可预期性 | 预约即知有无窗口；被挡时不知何时释放 | 到场前不知要排多久、轮到时剩余够不够 |

**硬规则（两种模式都遵守）**：

- **不得超售**：锁量模式「已锁(估)+已卸实收 ≤ 容量」恒成立；排队模式「已卸实收 ≤ 容量」恒成立。实称超窗口余量一律拒收；站长把容量调到低于已锁+实收也会被拒。
- **估重不能登记成已卸实收**：台账“实收”只累计过磅实称（本题实收合计 1.8+2.0=3.8 吨）；估重 2.5/2.0 吨仅用于锁窗，从不计入实收。
- **临时停收**：停收期间到场/过磅一律拒绝，在途预约成为线路上的真实阻塞，调度员可安排等待或改道。

### 主线二：转运站窗口预约

**A. 锁量模式（初始状态，无需重置）**

1. 登录调度员 `dispatcher/disp123`：右侧「转运站队列与受影响站点」可见 W1 窗口台账（已锁(估) 2.5t / 实收 0 / 剩余 1.5t）、BK-T1 已锁窗、**BK-T2 被挡**及 T2 线路上受影响的站点；左侧「锁量 vs 到场排队」面板按本题数据并列演算两种模式的可接车辆、等待顺序与容量释放时刻
2. 点演示按钮 **⑤ 时钟推进到 10:00**（窗口开启）
3. 登录司机 `driver1/drv123`（T1）：「转运站预约」中 **到场 → 过磅输入 1.8** → 实收 1.8t 入账，**释放 0.7t 锁量**，台账与事件日志可见 BK-T2 自动补锁成功
4. 登录司机 `driver2/drv123`（T2）：预约已变为“已锁窗”，**到场 → 过磅先输入 2.5** → **拒收**（超余量 2.2t，台账不登记）；**改输 2.0** → 成功，窗口实收合计 3.8t ≤ 4.0t（不超售）

**B. 临时停收与改道（先点 ① 重置并重放）**

5. 调度员点演示按钮 **⑥ W1 临时停收**（或站长在窗口管理中操作）→ 过磅/到场被拒；调度员「转运站队列与受影响站点」中 T1、T2 及其线路上未完成站点列为受阻
6. 对 T2 点 **安排改道** → 登录司机 `driver2/drv123` 看到改道安排并 **确认** → BK-T2 记“已改道”，城北转运站 W2 自动生成新预约并锁窗；站长（或按钮⑥）**恢复接收**

**C. 到场排队模式（先点 ① 重置并重放）**

7. 登录站长 `master/mst123`：右侧把城西转运站**切为到场排队** → 锁量全部释放，两条预约转为“已登记”
8. 调度员点 **⑤ 时钟到 10:00**；司机 T1 **到场**（第 1 位）、T2 **到场**（第 2 位）；T2 先过磅 → **被拒**（非队首）；T1 过磅 1.8 → T2 过磅 2.0 → 实收 3.8t，等待顺序严格按到场先后

**D. 窗口调整（锁量模式下）**

9. 站长把 W1 容量改为 2.0 → **被拒**（低于已锁(估) 2.5t，等同超售）；改为 5.0 → 保存成功，被挡的 BK-T2 立即补锁；时段也可同样调整，全部写入事件日志

## 关键规则实现

- **估重 ≠ 实称（收运）**：规划用估重；称重写入实称后，剩余容量不足必须停收并触发重排；已称重站点重排时按实称计算
- **估重 ≠ 实收（转运）**：窗口台账“已卸实收”只累计过磅实称；估重仅用于锁窗，不登记为实收
- **不得超售（转运）**：锁量模式「已锁(估)+实收 ≤ 容量」、排队模式「实收 ≤ 容量」恒成立；过磅超余量拒收、窗口容量调低到已锁+实收以下拒调
- **容量释放（锁量模式）**：过磅时刻释放「估重 − 实称」的锁量，被挡预约按预约先后自动补锁
- **到场排队（排队模式）**：到场先后决定过磅顺序，只有队首可过磅；容量在过磅时才按实称扣减
- **临时停收**：停收期间到场/过磅拒绝；在途预约进入调度员“受阻”列表（含受影响线路站点），可发等待/改道安排，司机确认后生效（改道自动生成目标站新预约）
- **回执幂等**：同一回执号（或同人同站同动作的同一二维码）重传只计一次，判定“重复”
- **迟到回执冲突**：站点已移交他人或已不在该车当前线路版本中 → 旧回执判定“冲突”，不改变站点状态
- **线路版本**：每次应用方案生成新版本（记录策略、原因、依据版本）；回执、通知均关联版本号，司机端与客服端可追溯到当前线路所依据的版本
- **通知重发判定**：承运车辆变更、到达时刻偏移 >5 分钟、同车相对顺序变化 → 需重发
